# Sub2API 官方出站身份伪装优化方案

## 一、结论与设计原则

推荐保留现有画像引擎，重做“身份分类、版本选择、执行边界、旁路约束和上线控制”五层，不推倒重来。

目标不是让所有官方域名请求都伪装成 Codex CLI，而是保证每个官方上游请求的以下要素属于同一个出站身份（下文称 `persona`）：

- 端点归属与请求行为；
- Header、Body 及字段顺序；
- TLS、HTTP/1.1、HTTP/2 或 WebSocket 传输画像；
- 触发时机、调用频率及连接生命周期。

必须遵守以下原则：

1. 目标态下，`codex-cli` 身份的请求只能由 `CodexEgressExecutor` 这个逻辑出口发送；迁移期只允许精确登记、可到期的 per-sink legacy 例外。
2. Executor 是身份和端点感知的逻辑边界，不等于某一个 HTTP 库；内部允许按 `TransportSpec` 选择 HTTPUpstream、req-profile 或 WebSocket backend。
3. `chatgpt-web/chrome` 等其他身份使用各自的受控 Plan 和执行入口，禁止错误迁入 Codex 画像。
4. 每个官方上游发送点必须声明 `persona`；已迁移 sink 的 route、身份、画像或定型凭证不一致时必须拒发，存量未迁移 sink 只能按精确 `legacy_observe` 基线记录并临时放行。
5. 未登记 route，以及 SinkID 缺失、未登记或绑定不符的 sink，在变更集 1C 后必须 fail-close；已登记且绑定正确但尚未迁移的 sink 按 per-sink 状态继续 observe，直到变更集 3 完成迁移。
6. Release 在一次账号尝试或独立系统调用开始时只解析一次，下游不得重新查询全局 active。
7. 目标态及已迁移 sink 中，调用方只能提交未定型的 Plan，不能取得最终请求后继续修改。
8. 运行时 Guard 与 source-to-sink 静态门禁必须同时存在；任一层都不能单独证明没有旁路。
9. 静态门禁从第一天禁止新增裸 sink；observe 只用于受控存量迁移，不能成为新增旁路窗口。
10. Guard 必须具有可审计的 per-sink 灰度、切换和回滚机制，不得只提供全局开或关。

## 二、目标架构

```text
HTTP/WS 入口、辅助端点、内部任务
        ↓
IngressSnapshot（脱离 Gin）
        ↓
OfficialRouteCatalog.Resolve(method, host, path, purpose)
        ├─ codex-cli
        │      ↓
        │  ReleaseCatalog.Resolve(purpose, mode)（只执行一次）
        │      ↓
        │  ResolvedCodexRelease / ReleaseBundle（不可变）
        │      ↓
        │  CodexEgressPlan（含 HeaderPolicy、BehaviorPolicy；不含 TransportSpec）
        │      ↓
        │  CodexEgressExecutor（唯一逻辑出口）
        │
        ├─ chatgpt-web/chrome
        │      ↓
        │  BrowserProfile + BrowserEgressPlan
        │      ↓
        │  ChatGPTWebEgressClient（browser persona 逻辑出口）
        │
        └─ 未登记或待分类 route
               ↓
           UnknownRoutePolicy 决策
             ├─ observe：变更集 1A 记录后放行
             └─ enforce：fail-close

逻辑执行入口
        ↓
PreparedRequest + FinalizationToken + TransportSpec
        ├─ HTTPUpstreamBackend
        ├─ ReqProfileBackend
        └─ WebSocketBackend
                 ↓
          persona-aware Runtime Guard
            物理 method/host/path/protocol 未登记 → UnknownRoutePolicy
            物理 route 已登记、SinkBinding 缺失或不符 → UnregisteredSinkPolicy
            以 Catalog 权威 binding 完成二次解析并匹配 → SinkEnforcementState
              legacy_observe | canary_enforce | enforced
                 +
          source-to-sink 静态门禁
```

### 1. OfficialRouteCatalog 与 persona

`OfficialRouteCatalog` 必须两阶段解析：先完全忽略请求声明的 purpose/persona/SinkID，按
`method + host + path + protocol` 匹配物理 route；再检查 SinkID，并以 `SinkCatalog` 中的
权威 purpose/persona/backend 完成精确解析。不能只按 host 判断，也不能先信任 context 中
尚未验证的 purpose，否则错误 purpose 会把 binding 问题降级为 `unknown_route`。

首批至少区分：

| persona/状态 | 已确认的端点范围 | 受控出口 | 处理原则 |
|---|---|---|---|
| `codex-cli` | Codex ReleaseBundle 中登记的端点闭集，包括 OAuth refresh | `CodexEgressExecutor` | URL、Header、Body、TLS、WS、状态和生命周期全部由同一个 Bundle 驱动 |
| `chatgpt-web/chrome` | privacy service 的 settings、accounts check、subscriptions | `ChatGPTWebEgressClient` | 保持 Chrome TLS/HTTP2 身份；**当前 wire 实测不正确，1B 修复**（见下） |
| 待分类 | PAT whoami、Agent Identity task register 等已发现但尚未完成身份举证的官方 route | 显式 legacy sink 基线 | observe 阶段记录并主动演练；完成端点、Header 和传输证据后才能归入 persona |
| 未知身份 | 未登记的官方 route | 无长期出口 | 变更集 1A observe 期间记录后放行并完成分类；enforce 后拒绝 |

privacy service 当前三个生产端点属于 `chatgpt-web/chrome`，不能迁入 `CodexEgressExecutor`：

- `PATCH /backend-api/settings/account_user_setting`
- `GET /backend-api/accounts/check/v4-2023-04-27`
- `GET /backend-api/subscriptions`

当前 `ImpersonateChrome()` 会安装一套 Chrome TLS/HTTP2/Header 模板，但版本和请求语义
都可能过时，不能仅凭工厂配置认定最终 wire 正确。

**变更集 0 已完成该验证，结论是当前 wire 不正确**，两处缺陷都需在 1B 修复：

1. **TLS 指纹版本过时**。`ImpersonateChrome()` 固定使用 `utls.HelloChrome_120`（2023 年底发布），而项目依赖的 utls v1.8.2 已提供到 `HelloChrome_133`。实测 supported_groups：120 为 `GREASE, X25519, P-256, P-384`，133 为 `GREASE, X25519MLKEM768, X25519, P-256, P-384`。真实 Chrome 自 124 起默认启用 X25519MLKEM768——当下不 offer PQ key share 的「Chrome」，仅凭 ClientHello 即可与真实浏览器区分。HTTP 层同样停留在 120（`sec-ch-ua` 声明 `v="120"`、UA 为 `Chrome/120.0.0.0`）。

2. **导航 Header 混入 XHR 请求**。req/v3 的 `chromeHeaders` 常量是为「浏览器打开页面」设计的：`sec-fetch-mode: navigate`、`sec-fetch-dest: document`、`sec-fetch-user: ?1`、`upgrade-insecure-requests: 1`、`accept: text/html,...`。privacy service 只覆盖了 `sec-fetch-*` 三项，其余原样发出，形成「XHR 的 sec-fetch-* + 导航的 Sec-Fetch-User」这种真实浏览器不会产生的组合。另有 `sec-ch-ua-platform: "macOS"` 与 `accept-language: "zh-CN,zh;q=0.9"` 为硬编码，与部署环境和账号地域无关。

`SetTLSFingerprint` 是 req/v3 的公开 API，在 `ImpersonateChrome()` 之后追加即可覆盖，已实测生效。但 TLS 版本、版本 Header、请求语义 Header 三者必须同批修改：只改其一会制造「TLS 声称 133、HTTP 声称 120」的新不一致。

以下低频 route 必须进入前置身份清单，不能等运行时偶然触发后再处理：

- `GET auth.openai.com/api/accounts/v1/user-auth-credential/whoami`
- `POST auth.openai.com/api/accounts/v1/agent/{runtime}/task/register`

它们不应仅因为位于官方 host 就自动归入 `codex-cli`；必须分别核对官方行为、Header 和传输证据。

### 2. 包边界与依赖方向

fork 自有的画像和执行核心应下沉到 `backend/internal/officialegress`，避免继续堆积在上游高频变化的 `service` 包。

`internal/officialegress` 及其子包负责：

- `Persona`、`RouteKey`、`SinkID`、`SinkBinding`、`OfficialRouteCatalog` 和 `SinkCatalog`；
- 纯画像 `ProfileSpec`、`purpose + mode` ReleaseGraph、ReleaseBinding 与不可变快照目录；
- 中立的 ResolvedRelease/ReleaseBundle 值类型，以及 ReleaseProvider、RequestCompiler port；
- ReleaseCatalog、schema 和 compiler 的正式实现；
- PreparedRequest、FinalizationToken 和 TransportSpec；
- Executor core、UnknownRoutePolicy、UnregisteredSinkPolicy、SinkEnforcementState、SinkGuardOverride 和违规事件模型；
- HTTPUpstream、req-profile、WebSocket 等中立 transport port。
- `internal/officialegress/adapter/*` 中闭集、受信任且有 wire 契约测试的 adapter。

`service` 继续负责：

- Gin/HTTP 入站适配；
- Account、配置和账号尝试解析；
- 账号选择、故障转移和 TokenProvider；
- 业务状态、BehaviorPolicy 和 Plan 组装；
- 将业务对象转换为不依赖 `service` 类型的 Snapshot/Plan。

`repository` 负责：

- HTTPUpstream、req/v3 client pool、代理和连接池等底层资源；
- 按窄 port 暴露资源，不持有 persona、Release 或 route 规则；
- 不自行复制画像、Header、Body 或 route 规则。

依赖目标为：

```text
service ─────────────────────→ officialegress core
repository ──────────────────→ officialegress core 的窄 port
officialegress/adapter/* ─────→ officialegress core + repository 资源
wiring ──────────────────────→ 为 Executor 注入闭集 adapter
```

以上只描述 official egress 这一条依赖缝，不要求在同一变更集中消除仓库既有的全部 `repository → service` 领域 port；但不得再为出站画像或 Executor 新增这种依赖。

`officialegress` 不得 import `service` 或 `repository`。Gin、Account、配置、仓储和业务状态适配不能整包搬入该目录。

仅移动文件无法自动解决依赖问题。Executor 边界必须使用中立 Plan、Release/Compiler port
和 transport port，不能向业务调用方暴露可被继续修改的 `*http.Request`、`*req.Client`
或具体 repository 类型。

真正操作 socket 的 adapter 物理上必须读取并发送完整 method、URL、Header 与 Body，
因此 adapter 属受信任边界。用只读 getter 包装成 `SealedRequest` 并不能让它“不可信”；
约束来自 adapter 包闭集、AdapterID/FinalizationToken 校验、wire 契约测试和 source-to-sink
静态门禁，而不是形式上的类型不可及。

为避免变更集 1B 依赖尚未下沉的 service 画像，变更集 1A 先定义中立类型和过渡 port：

```text
ReleaseProvider.Resolve(purpose, mode) → ResolvedRelease
RequestCompiler.Compile(release, plan) → CompiledRequest（未签名）
```

变更集 1A 由 service 临时实现这两个 port，并通过 wiring 注入 Executor；变更集 2 再把 ReleaseCatalog 和 compiler 的正式实现下沉并删除临时适配层。

compiler 只做语义定型，产出**未签名**的 `CompiledRequest`；Release、TransportSpec、
连接池身份与 `FinalizationToken` 一律由 Executor 在 `officialegress` 包内注入并私有签发。
签发函数不导出——这样即使 compiler 临时位于 `service` 包，也无法伪造定型凭证。

### 3. ReleaseCatalog

启动时确定性构建全部 Codex 版本：

- 不使用依赖分散 `init()` 时序的注册模型；
- active/previous 指向完整 release ID；
- 编译并校验 build、wire、endpoint、feature、TLS、字段序和 digest；
- 任一缺失直接启动失败。

后续可改成 `go:embed` 版本数据文件，但这不是 P0。

变更集 0 已先把正式实现所需的证据拆成四层 build-tag 契约：

```text
SnapshotDoc → ProfileSpec
official-client registry → ReleaseGraph(purpose + mode)
sink-baseline.json → ReleaseBinding
三者 + 显式 release purpose/mode → EvidenceBundle
```

其中 `ProfileSpec` 只承载画像真实字段，禁止出现 purpose、backend、RetryPolicy、selector
或部署事实域；`EvidenceBundle` 也只做证据连接，不冒充可执行 Release。后续生产
`ResolvedRelease` 还必须显式合入 ExecutionPolicy、DeploymentSupportPolicy 与
ReleaseSelectionPolicy，不能由画像转换器填默认值。

### 4. 不可变 ReleaseBundle

一次解析后全链路传递，至少包含：

- mode、version、release/profile ID、digest；
- User-Agent、originator 及受支持的身份变体；
- HTTP/WS endpoint plans；
- Header、Body 字段序及 feature；
- TLS、压缩、连接生命周期；
- endpoint 对应的 TransportSpec。

下游禁止再查询 `activeOfficialCodexVersion()`，也不再使用包级 active 字段序。

OAuth refresh 当前已经由画像构造 URL、闭集表单、Header 和 strict H1/TLS，不是 P0 旁路；但它硬编码 active，必须在本阶段改为消费调用已经选择的 ReleaseBundle。迁移不能顺手更换其已验证的 req-profile backend。

画像字段保持私有，只暴露值或深拷贝 getter。不能再把“调用方不得修改共享指针”作为唯一不可变保证。

画像快照以 `version + digest` 为不可变主键；版本号相同不代表 Release 相同。当前 OAuth
active/previous 都是 0.145.0，但 previous 使用 xterm Build 和不同 wire digest，发布选择
必须按 `purpose + mode` 定位，不能按版本字符串折叠。

### 5. Persona Plan 与 Header 所有权

调用方提交 persona 对应的 Plan。`CodexEgressPlan` 至少包含：

- endpoint、账号、Body、状态和调用生命周期；
- `IdentityMode`；
- 规范化并深拷贝后的 `ResolvedHeaderOverrides`；
- `HeaderPolicy`；
- `BehaviorPolicy`。

`TransportSpec` **不属于 Plan**：它由端点画像决定，在 Executor 签发 PreparedRequest 时
从 ReleaseBundle 注入。放进 Plan 等于允许调用方指定 backend，绕过画像声明的传输形态。

建议明确以下身份模式：

- `CodexOAuthStrict`
- `CodexAPIKeyMimic`
- `OfficialClientProxy`
- `GenericOpenAI`

Header 按所有权和身份模式确定优先级：

| Header 类别 | 所有者与规则 |
|---|---|
| Transport、Auth、Body framing | 系统所有，账号永远不能覆盖 |
| Release identity | strict、mimic、proxy 模式由画像最终决定 |
| Account extensions | 普通 API Key 可按现有产品规则覆盖；mimic/proxy 只允许非保护字段 |
| Endpoint closed set | OAuth 严格官方端点最终删除画像闭集之外的字段 |
| Ingress headers | 最低优先级，只能进入明确允许的字段 |

必须保留当前产品语义：

- OpenAI OAuth 的账号 Header Override 为 no-op；
- API Key Codex mimic 下，账号不能覆盖 User-Agent、originator、版本和 `x-codex-*` 等身份头；
- API Key mimic 当前允许保留非保护的自定义 Header，迁移时不能静默删除；
- Authorization、Content-Type、Host、长度及连接控制字段始终由系统决定。

Header Override 是 Plan 的冻结输入，由 Executor 统一解析冲突；不再允许调用方在最终请求上追加。

### 6. BehaviorPolicy 与 WHAM-first

内部探针不能只验证“长得像 Codex”。Plan 还必须声明行为类型，例如：

- 用户业务请求；
- 管理端显式测试；
- quota/usage 查询；
- OAuth refresh；
- 后台主动探针。

对每个非用户直接触发的请求，必须记录并测试：

- 官方客户端是否存在等价行为及证据来源；
- 触发条件、最短间隔、随机抖动和并发上限；
- 是否产生模型调用、会话状态或计费副作用；
- 是否可以从真实业务响应被动提取结果；
- 是否有更符合官方行为的专用端点。

当前普通 OAuth 用量刷新会构造 `/responses` 的合成 `hi` 请求，并按缓存状态周期触发。目标方案不再把三条替代路径并列，明确采用 WHAM-first：

1. 普通 OAuth 默认请求 usage-only `GET /backend-api/wham/usage`。
2. 普通 OAuth 从顶层 `rate_limit` 提取 Codex 窗口；Spark shadow 继续从 `additional_rate_limits.codex_bengalfox` 提取。
3. 只有响应为 2xx、目标 RateLimit 非 nil、至少一个窗口结构完整且窗口时长属于已知闭集时，才接受并落库。
4. 窗口归类必须按明确的 `limit_window_seconds` 规则，不得继续用“短于 6 小时算 5h、其他都算 7d”的宽松阈值吞掉未知 30d 等窗口。
5. 周期刷新使用 usage-only 方法，不能直接复用会额外查询 reset-credit details 的完整 `QueryUsage`。
6. WHAM 与 Responses WSv2 无关，普通 OAuth 的 staleness 判定不得继续受 WSv2 开关限制。
7. 被动业务响应中的限额 Header 继续作为补充、交叉验证和故障时的已有快照来源。
8. 缺少 account ID、端点能力不兼容、响应为空或窗口未知等兼容性情况，可以进入同一次刷新调用内的受控 fallback；凭据失效、安全错误和明确不可重试错误不得被 fallback 掩盖。
9. fallback 必须发生在同一次刷新函数内，避免预先写入的 probe TTL 把后续重试压住。
10. `/responses` 探针只有完成 Codex 画像定型、进入 Executor、具备独立遥测和删除期限后，才可作为临时 fallback；不能继续使用普通 Go TLS 客户端。

被动响应不替代 WHAM 的官方行为证据，但可以减少主动查询频率。不能把“迁入 Executor”本身当作后台主动请求已经合理的证明。

### 7. Persona Executor 与多 backend

`CodexEgressExecutor` 是 `codex-cli` persona 唯一允许的逻辑出口，而不是唯一 HTTP 库或唯一 transport 实现。

调用方只提交 `CodexEgressPlan`，不能取得定型后的裸 `*http.Request` 再继续修改。重试时由 Executor 根据同一个 Bundle 重新构造 PreparedRequest。

Executor 根据端点画像编译出的 `TransportSpec` 选择 backend：

| backend | 典型用途 | 迁移原则 |
|---|---|---|
| `HTTPUpstreamBackend` | Responses、WHAM、辅助 HTTP 端点 | 保留现有 TLS/H1 和代理能力 |
| `ReqProfileBackend` | OAuth refresh 等已经通过 req/v3 pool 安装 TLS profile 的路径 | 先包装为 adapter，不强制换栈 |
| `WebSocketBackend` | Responses WS、连接池和 fallback | Bundle、压缩、连接 key 和帧行为必须连续 |

persona 与发送栈是多对多关系：同一个 Codex persona 可以使用多个 backend，同一个 req/v3 或 HTTPUpstream 基础设施也可以承载不同 persona。身份不能由“用了哪个库”推断，必须由 RouteCatalog、Plan 和定型凭证共同决定。

每个 backend 在发送前都必须验证：

- persona 和 endpoint 与 TransportSpec 匹配；
- FinalizationToken 属于当前 Bundle/Profile；
- profile digest 与连接池 key 一致；
- 最终请求只发生 Token 中 `WireNormalizationPlan` 明确授权的 adapter 变换。Token 绑定
  adapter-aware 语义摘要和 normalization plan；HTTP lowercase、Go 默认 User-Agent
  抑制哨兵及 Codex WS compression offer 可以按计划等价变换，其他 Header/URL/Body
  修改仍必须拒发。不得继续要求“适配前字节摘要 == 最终 wire 字节摘要”。

replayable Body 的摘要覆盖精确内容字节；single-use stream 不得在 Prepare/Guard 中预读或
复制，只绑定不可伪造 capability 与 ContentLength，并强制 `MaxAttempts=1`、
`Replayable=false` 和 PreparedRequest 单次消费。RequestCompiler 必须交还同一个私有
capability；重新构造的同长度 stream 也必须被 Executor 拒绝。

这会从架构上避免：

- attach 后漏 finalize；
- finalize 后继续补 Header；
- Header、Body 和 TLS 来自不同版本；
- 辅助端点自行选择普通客户端；
- 重试或 fallback 过程中切换 persona。

`ChatGPTWebEgressClient` 对 browser persona 提供相同的“Plan → 定型 → 发送”边界，但使用独立 BrowserProfile 和 Chrome transport，不复用 Codex ReleaseBundle。

只有在抓包和 wire 测试证明行为完全等价后，才能考虑合并发送栈；统一 Executor 不能成为更换已正确 transport 的理由。

### 8. 运行时 Guard、per-sink 灰度与回滚

Guard 只负责最终身份约束，不承担 Gin、账号或 Body 业务规范化。它先计算事实和违规，再由对应策略决定记录放行或拒发：

- 先解析物理 route，再检查 sink 登记，最后以 Catalog 的权威 binding 校验请求声明；
- 检查 Bundle/Profile 定型凭证、profile/digest 与连接池身份；
- 对已经进入 Executor 的请求执行最终 header casing 和协议 wire 适配；
- 未登记 route 按独立的 `UnknownRoutePolicy` 决策；
- route 已登记但 SinkID 缺失、sink 未进入 `SinkCatalog` 或绑定元组不符时，按独立的 `UnregisteredSinkPolicy` 决策；
- route 已登记且完整 `SinkBinding` 匹配时，按该 sink 的 `SinkEnforcementState` 决策。

不能再用一个全局 `observe/enforce` 开关描述所有 sink。建议采用两个未知项策略和一个已登记 sink 状态，三者彼此正交：

```text
official_egress_guard.unknown_route_policy = observe | enforce
official_egress_guard.unregistered_sink_policy = observe | enforce

SinkEnforcementState =
  legacy_observe
  canary_enforce
  enforced
```

`SinkCatalog` 是全部已识别 sink 的登记表；legacy 基线只是其中尚未迁移、允许临时按原链发送的精确子集。已迁移 sink 应从 legacy 基线删除，但仍保留在 `SinkCatalog` 并进入 `canary_enforce/enforced`，因此“未在 legacy 基线”不等于“未登记 sink”。

`SinkID` 必须在业务调用点生成或显式绑定，随 Plan/context 穿过共享 facade、backend 和重试链，一直传到 terminal Guard。共享 `HTTPUpstream`、req/v3 pool 或 RoundTripper 不能用自己的通用 ID 覆盖业务调用点 ID。在 route 已登记的前提下，Guard 必须校验完整的 `SinkID + RouteKey + persona + backend` 元组：缺少 ID 记录 `missing_sink_id`，ID 未登记记录 `unregistered_sink`，元组不符记录 `sink_binding_mismatch`；三者均按 `UnregisteredSinkPolicy` 决策，不能借用其他已登记 sink 的状态。

Guard 挂在共享栈出口，因此必须先做独立的 `EgressScope` 判定。受管证据来自官方 persona
命名空间、已登记且非 facade 的业务 binding/purpose，或可信 Executor token；不得按 host
闭集猜测。判为 out-of-scope 的第三方流量记录 `out_of_scope_passthrough` 后原样放行，且
不能继续产生 `unknown_route`。

Guard 必须按以下顺序决策：

0. 不属于官方 persona 管辖域：记录后原样放行并停止判定；
1. managed scope 内物理 `method + host + path + protocol` 未登记：使用 `UnknownRoutePolicy`；
2. 物理 route 已登记，但 SinkID 缺失、sink 未进入 `SinkCatalog`，或用 Catalog 权威 binding
   二次解析后完整元组不符：使用 `UnregisteredSinkPolicy`；
3. 完整 `SinkBinding` 匹配：使用该 sink 的 `SinkEnforcementState`。

active/previous 只负责画像回滚，不能冒充 Guard 回滚。两个未知项策略不能覆盖已登记 sink 自己的状态。

#### legacy_observe

- 所有发送栈都执行 Guard，但尚未迁移的显式 legacy `sink_id/callsite` 可以记录后按原链放行。
- legacy sink 即使 route 已登记，也可以暂时缺少 Executor 或 FinalizationToken；这些违规必须完整记录。
- 新增 sink、基线外调用点不能取得 `legacy_observe`，静态门禁必须立即失败。
- observe 只降低迁移期间的生产中断风险，不能证明 route 枚举完整。

#### canary_enforce

- 仅对已经完成迁移、具备对应 persona 逻辑出口签发的 FinalizationToken 且持有可复算
  `MigrationReceipt` 的 sink 启用。Receipt 必须覆盖 binding 的每一条 route，并冻结 binding
  digest、authority/TokenIssuer、Adapter/Transport、画像证据、实际 wire fixture 路径、
  执行验证产物路径与源码候选；CI 和运行时读取实际文件并重算摘要，业务调用者不能用枚举
  或一段格式合法的虚构 SHA 自行声明已完成迁移。
- `codex-cli` 必须满足 `codex_profile + Codex Executor receipt`；`chatgpt-web` 必须满足
  `external_persona + ChatGPTWebEgressClient receipt`。`transport_only`、`unclassified`、
  `missing`、`not_applicable` 永远不能进入 canary/enforced；其中 `transport_only` 也不能
  生成 EndpointID/ReleaseSelection。
- 按稳定的实例、账号、route 或 sink hash 选择 canary，避免同一请求在重试时改变模式。
- canary 范围执行 enforce，其他流量继续 observe。
- canary 失败必须能定位到 `sink_id + route + persona + backend`，不得只返回笼统网络错误。

#### enforced

- enforced 收据必须引用同 Sink 已存在的 canary 收据摘要和可复算 canary acceptance 产物，
  禁止从 legacy 直接签发 enforced。
- 仅表示该 sink 已完成迁移和验证；错误 Executor/backend、缺少凭证、digest 不一致或定型后修改全部拒发。
- 已进入 `enforced` 的 sink 不得因其他 sink 尚未迁移而退回长期 legacy 基线。
- 变更集 1C 的“全量”只指当时已经迁移的 sink 集合，不包含要到变更集 3 才迁移的主链。
- 所有 Codex sink 真正全量 enforced 的时间点是变更集 3 验收末尾。

#### 已登记 route + 无效 SinkBinding

- 运行时无法判断该 sink 是变更集 0 漏登记的存量，还是部署中引入的新增旁路；只有静态门禁能结合 bootstrap commit 与代码差异完成这一区分。
- 变更集 1A 设置 `UnregisteredSinkPolicy=observe`，所有这类发送均按 `missing_sink_id`、`unregistered_sink` 或 `sink_binding_mismatch` 记录后放行，确保首次接入 Guard 不改变生产结果。
- 变更集 1A 观察期发现的遗漏，只能在证明调用点已存在于 bootstrap commit、补齐 persona/route/backend/责任人并通过审核后，加入 `SinkCatalog` 和必要的 legacy 基线。
- 完成自动扫描、观察窗口和低频路径演练后，变更集 1C 将 `UnregisteredSinkPolicy` 切为 `enforce`。此后任何 SinkID 缺失、未登记或绑定不符的 sink 均拒发，无须在请求期判断其历史来源。
- 若永久 observe，命中已知 route 的新增普通 client 或半旁路会失去运行时第二道防线，因此不能把区分职责永久完全交给静态门禁。

#### 未登记 route

- 变更集 1A 首次部署时，`UnknownRoutePolicy=observe`，所有命中均记录 `unknown_route` 后放行，确保首次接入 Guard 不改变生产结果。
- 完成 route 清单、主动演练和 canary 后，变更集 1C 将 `UnknownRoutePolicy` 切为 `enforce`。
- 已登记但尚未迁移的 route 不属于 unknown，继续按其 sink 的 `legacy_observe` 状态运行。
- 新代码命中未知 route 仍由静态门禁阻断，不能借运行时 observe 上线。

OAuth authorization-code exchange 虽与 refresh 共享 `POST auth.openai.com/oauth/token`，
当前只有 `transport_only` 证据：Catalog 可以登记其物理 route，但必须留下空 EndpointID，
ReleaseSelection 必须失败，不能借物理相同组合成 refresh Body 契约。API-Key Codex mimic 与
自定义 base URL 不属于 OAuth persona，不得绑定 OAuth SinkID。OAuth Responses 资源子路径
只有取得正式画像证据并登记精确模板后才能发送；当前仅根路由与 `/compact` 可用，其他
`/{id}`、`/{id}/cancel` 等子路径必须在业务层发送前明确拒绝，不能留到 1C 意外 fail-close。

#### 单个 sink 的切换条件

不能只以“观察若干天没有违规”作为 sink 进入 enforced 的依据。每个 sink 必须同时满足：

1. route/persona/backend 已登记且证据完整；
2. 已通过 Executor 产生 FinalizationToken；
3. persona wire、静态门禁和自测负例全绿；
4. 该 sink 的 canary 没有 wrong-executor、missing-credential 或 digest 冲突；
5. 对应低频、fallback 和错误恢复分支已经主动演练。

#### 回滚

- 回滚以单个 `sink_id` 为粒度，将 `enforced → canary_enforce`；如需紧急 observe，使用独立且有到期时间的 `SinkGuardOverride=observe_until`，不能把 observe 发明成第四个 `SinkEnforcementState`。
- `canary_enforce` 存在时 `canary_percent` 必须为 `1..100`；禁止用 0% 把 state downgrade 变成无期限全量 observe。
- 临时例外必须具有到期时间、责任人和 reason code；过期自动恢复原状态。
- `UnknownRoutePolicy` 或 `UnregisteredSinkPolicy` 如需紧急回到 observe，必须限制实例、route/sink 范围和到期时间，不允许永久全局放行；unknown route 必须额外绑定目标 `EscapedPath` 的 SHA-256，日志模板不得作为覆盖匹配键。
- 不提供静默的全局 off；回滚后继续记录全部违规指标。
- 其他已经稳定 enforced 的 sink 不随单个 sink 回滚而降级。

Guard 日志只记录稳定 reason code、sink ID、method、规范化 host/path 模板、声明/解析 persona、backend 和 profile digest。禁止记录 query、Body、Token、Cookie 和账号密钥。样本必须有界去重，同时保留总量指标。

Guard 只挂四类发送栈的 terminal 出口，不逐个侵入 180 条扫描候选；出口按
`EgressScope`/RouteCatalog 判定是否受管，SinkID 只在 in-scope 业务调用点绑定：

- `net/http` 使用受控 RoundTripper；
- repository `HTTPUpstream` 在 `Do/DoWithTLS` 前校验；
- req/v3 使用受控工厂及发送前 hook；
- WebSocket 在 Dial 前校验 Bundle、persona 和连接 key。

RoundTripper 无法发现另建的普通客户端，也无法覆盖 req/v3 和全部 WS 实现，因此不能用一个 RoundTripper 代替完整旁路约束。

### 9. source-to-sink 静态门禁

门禁必须从所有具备网络发送能力的库、类型和工厂出发，同时覆盖 terminal transport sink 与仓库 facade 调用点，不能只搜索若干函数名或已经引用伪装符号的文件。

首批 sink 清单至少包含：

- `net/http.Client.Do`、`http.Get/Post/PostForm/Head`、`RoundTripper.RoundTrip` 及仓库共享 httpclient pool；
- repository `HTTPUpstream.Do/DoWithTLS`；
- req/v3 的 `Request.Get/Post/Patch/Put/Delete/Head/Options/Send/Do`、`Must*` 及 `Client.Do` 等终态调用；
- 由 req/v3 client pool 取得底层 `http.Client` 后执行的 `Do`；
- coder/gorilla 等所有 WebSocket Dial；
- 仓库中存在的直接 `net.Dial`、`tls.Dial` 或其他自建传输。

变更集 0 必须提供可重复运行的类型感知扫描器：

1. 使用 `go/packages + go/types + AST`，按包路径、接收者类型和方法识别调用，不能只按 `Do`、`Send` 等 selector 名做文本匹配；
2. `--bootstrap` 扫描全部生产网络 sink，生成候选全集；literal、const、constructed、dynamic 和 unknown 目标都必须输出，不能只保留已经能解析为官方 host 的调用；
3. 变更集 0 必须建立项目 facade 的完整限定签名清单，并扫描这些 facade 的业务调用点；函数值、接口转发或多层包装无法由直接类型调用覆盖的部分，再使用调用图或 SSA 补充，但所有残余盲区必须在变更集 1C enforce 前消除或由明确的运行时拦截覆盖；
4. 对关键 GOOS、build tag 和生成代码执行扫描矩阵；无法完成类型检查的生产文件必须进入语法候选兜底，不能静默跳过；
5. 候选项必须经人工补齐 persona、route、backend、状态和迁移责任后，才能进入 `SinkCatalog` 或 legacy 基线；扫描命中本身不等于身份分类已经正确；
6. bootstrap 完成后保留扫描器并接入 CI，持续复算新增、消失及调用目标变化，不能将其作为运行一次即删除的脚本。

机器可读基线至少记录：稳定 `sink_id`、相对文件与所属函数、完整 callee/receiver、规范化 AST 指纹、terminal/facade 类型、目标解析状态及 method/host/path、persona、route、backend、EnforcementState、责任人、迁移变更集和到期条件。`sink_id` 不应依赖易漂移的行号；同一函数内的同类调用使用结构路径或显式注解消歧。

门禁检查：

1. 目标可能为官方 host 的发送点是否声明 persona；
2. route 是否在该 persona 的闭集中；
3. 是否使用该 persona 允许的 Executor、client factory 或 backend；
4. 动态 URL 是否同时具有运行时 Guard；
5. 新增网络库或发送调用形态是否同步登记到 sink 清单。

变更集 0 的扫描结果形成带 `bootstrap_commit` 的候选快照，人工分类后生成初始
`SinkCatalog` 和 provisional legacy 基线。由于扫描器和 inventory 产物晚于锚点提交，1A
必须另建不可变 bootstrap lock，冻结 commit tree、inventory 原文摘要与执行回放的扫描
算法摘要，不能假装锚点提交本身已经包含这些产物。

生命周期拆成独立、可交叉校验的 `ImmutableBootstrapInventory`、
`CurrentCandidateInventory`、`SinkCatalog`、`LegacyManifest`、`SupplementReceipt` 与
`Removal/MigrationReceipt`。观察期若发现扫描遗漏，只能在证明调用点已存在于
`bootstrap_commit` 后补录；收据必须冻结 file/function/callee、AST 指纹、
persona/route/backend/owner、历史源码 blob 摘要和审核信息，生产 Catalog 必须确定性合并
同一份收据，不能仅让扫描器读取。同一时期新增的代码不能借此进入 legacy。

Catalog amendment 同样必须冻结 source candidate 的 file/function/callee、AST 指纹与历史
源码 blob 摘要，并在 clean bootstrap archive 中复算。迁移型 RemovalReceipt 必须引用真实
存在、覆盖对应 candidate 与 replacement Sink 的 MigrationReceipt；格式合法但不存在的
摘要不能作为合法减法路径。

变更集 1A 验收后封存 legacy 基线并遵守“只减不增”：

- 基线外新增裸 sink 立即使 CI 失败；
- 已迁移 sink 从基线删除后不得重新加入；
- 同一文件中新增第二个调用点不能借用文件级基线；
- CI 禁止自动更新基线；候选消失必须有冻结原候选的 RemovalReceipt（dead-code 删除）或
  MigrationReceipt（已迁移替代），陈旧、未知或仍存在调用点的收据失败；调用目标或 AST
  指纹变化必须重新审核。

sealed 时生成独立 `legacy-seal-receipt`，冻结 `legacy-ceiling`、
`pre-bootstrap-supplements` 原文 SHA-256、bootstrap commit/tree、实际受保护 base commit、
`sealed_at` 与审核信息。
本地门禁复算摘要，CI 必须再与受保护目标分支的 base commit 比较；基准一旦 sealed，receipt、
ceiling 与 supplements 均逐字节不可变，不能通过同一工作区内协调修改三份文件重写历史。
Git object ID 必须使用同一完整小写十六进制判据，支持 SHA-1 的 40 位与 SHA-256 的 64 位；
首次封存收据必须绑定 CLI 从 Git 实际解析出的 base ID。CI 还必须读取受保护 base 的
`legacy-baseline`，强制当前 baseline 是上一受保护 baseline 的子集，而不只是初始 ceiling
的子集。每个减少项都能追溯到 MigrationReceipt/RemovalReceipt；已删除 SinkID 不得重新
加入，facade 和 dead-code 只留在 Evidence Catalog，不进入运行时 legacy allowlist。

“只减不增”只约束 legacy 基线，不禁止受审新增 `SinkCatalog` 条目。新增 sink 必须先部署 route/Catalog 登记，再部署携带对应 `SinkID` 且经过 Executor 的调用代码，并从 canary 开始；删除时先移除调用代码，再删除 Catalog 条目。bootstrap 后新增 sink 不得进入 `legacy_observe`。

门禁必须带自测负例，证明能发现：普通 `http.Client`、`DoWithTLS` 半旁路、req/v3 直发、req/v3 底层 client 直发及 WS 直拨；同时用 `sync.Once.Do`、singleflight 和数据库 `Do` 等负例证明类型判据不会按方法名误伤。

现有台账门禁继续用于文档同步，但不再承担端点覆盖证明。

## 三、建议实施顺序

严格按一个变更集一个变更集推进；每个变更集完成验收后再开始下一个。

### 变更集 0：身份、包边界与发送面基线

此阶段只形成设计和测试输入，不修改生产行为：

- 建立完整的官方 `host + method + path + purpose → persona` 分类表；
- 把 PAT whoami、Agent Identity task register 和其他低频 route 纳入清单；
- 实现基于 `go/packages + go/types + AST` 的可重复 sink 扫描器，首批固化项目 facade 完整限定签名清单，并为函数值、接口转发和多层包装保留调用图/SSA 扩展点；
- 扫描器必须把 `NewRequest/NewRequestWithContext` 的 method/URL 与后续
  `Do/RoundTrip/HTTPUpstream` 的具体请求参数绑定；用反向变异证明单独修改 method、host
  或 path 都会造成基线漂移，不得用“函数体内出现过官方 host”冒充数据流证据；
- 以 `darwin/arm64`、`linux/amd64` 生产构建矩阵复算发送面，并把类型检查失败文件显式
  记入 syntax fallback；不能让当前平台或类型信息缺失静默缩小扫描范围；
- 运行扫描器 `--bootstrap`，枚举 terminal、facade、client factory、动态 URL 和未知目标，生成带 `bootstrap_commit` 的候选全集；
- 人工审核候选全集，形成初始 `SinkCatalog` 与 provisional legacy 基线，补齐稳定 sink ID、persona、route、backend、状态、责任人和迁移期限，并定义 `SinkID + RouteKey + persona + backend` 绑定元组；
- 为每个 route 指定允许的 transport backend，而不是假设一个 persona 只对应一个栈；
- 固化 Header 所有权及 Override 优先级矩阵；
- 为每类内部探针确定行为来源、触发条件、频率和 fallback 策略；
- 固化 `internal/officialegress` 的包 API、依赖方向和禁止依赖；
- 建立 0A `ProfileSpec`：对原始画像做 canonical 无损往返、逐叶 digest 与深不可变测试；
- 建立 0B `ReleaseGraph`：从 official-client registry 按 `purpose + mode` 导出 active/previous，
  快照按 `version + digest` 不可变保存，并执行 `ObservedEnums ⊆ EngineSupportedEnums`；
- 建立 0C `ReleaseBinding`：从 sink 基线确定性聚合业务 Sink，不从画像推导 purpose、backend
  或 RetryPolicy；
- 建立 0D `EvidenceBundle`：显式连接 binding、发布节点和画像 endpoint，拒绝 HTTP/WS、
  persona、facade、快照或 route 误接；端点证据必须区分 `codex_profile` 与
  `transport_only`，不能因 authorization-code exchange 与 refresh 共用 `/oauth/token`
  就冒充同一 Body 契约；本层不生成可发送请求；
- 固化 UnknownRoutePolicy、UnregisteredSinkPolicy、per-sink EnforcementState、违规 reason code、观测指标、切换条件和回滚规则；
- 为 Codex 与 Chrome persona 准备最终 wire 证据及测试夹具。

验收：扫描器可确定性复跑，并通过各发送栈命中、同名非网络方法不误报、请求事实反向

#### 6.1 正式版本数据与内容寻址

正式目录固定为：

```text
officialegress/catalogdata/runtime/
├── release-catalog.json
├── release-graphs/
│   └── <sha256>.json
├── snapshot-catalogs/
│   └── <sha256>.json
└── profiles/
    └── <version>/
        └── <sha256>.json
```

- Profile 使用 `version + 官方画像 digest` 寻址，并在 SnapshotCatalog 中另存原始 blob

#### 6.2 单个 attempt 的 Body document 边界

边界从 `prepareOfficialCodexSemanticAttempt` 开始，经 compiler-owned 字段抽取、Compiler
校验／omit／注入／排序，到产生最终 replayable Body 字节结束。它只包含已经进入
officialegress Compiler 的 HTTP/WS replayable JSON；不包含 Chat Completions、Messages、
Anthropic 等入站兼容转换，不重构上游 WS 兼容管线或 service 业务策略清洗。
`raw_bytes`、single-use stream 完全保持原路径；`form_urlencoded` 本变更集保持原实现。

Body 契约固定如下：

1. “一次解析”指每个 replayable attempt 对顶层 JSON object 只做一次结构解析；标量或
   `client_metadata` 等嵌套小对象允许按需解码一次，但不得再次解析整个 Body；
2. “一次序列化”指最终完整 Body 只进行一次有序输出；注入值可由同一 writer 编码，
   不得先重建完整 Body，再交给 Compiler 重排重编码；
3. 顶层解析完成后，先对全部**解码后字段名**执行全局 duplicate 检查，再允许删除
   compiler-owned 字段、omit、注入或闭集校验；即将被删除的字段也不能隐藏重复；
4. duplicate fail-close 只保证“进入该 attempt 边界的 Body 字节”。边界前 service map
   解码可能已经折叠原始入站重复键，本变更集不声称端到端原始入站 duplicate fail-close；
5. 内部模型为不可变 source bytes、有序字段索引、duplicate 校验证据和 attempt-local
   dirty overlay。原始字段和值不可由调用方修改；失败后原 document 不变；retry 从同一
   语义 Body 创建新 document；`CodexEgressPlan.clone()` 不共享可写 map 或 dirty 状态，
   不得携带上一 attempt 注入的 metadata、prompt cache key 或 refresh token；
6. replayable Body 在 officialegress 包内共享不可变 backing：外部构造复制一次，Plan、
   CompiledRequest、PreparedRequest 内部传递不再整段复制；公开读取仍返回副本，包内只提供
   不可写 view。修改构造方原始切片或公开读取返回值均不得污染内部，并发 clone/Prepare、
   多次 `GetBody` 必须一致；single-use capability 行为不变。

#### 6.3 性能、错误与基线验收

- 生产实现修改前先冻结非 clean workspace 的完整路径闭集、存在状态、类型、权限、
  SHA-256、路径集合指纹、HEAD/HEAD tree、变更集 5 post final-wire 三件套、正式 Catalog
  blobs、benchmark fixture 与原始结果；变更集 5 的 56 份 post 只读引用，不得重新生成；
  变更集 6 在自己的目录生成 post，并以空允许列表和变更集 5 post 比较；
- 正确性单测／mutation 与 benchmark 分离。Body 固定建立 large unchanged、large dirty、
  retry、open WS 四项 benchmark 并 `SetBytes`；Catalog 固定建立 ReleaseCatalog、版本画像、
  endpoint 三项 benchmark；
- pre/post 各 `-count=10`，保存原始输出并用 benchstat；冻结 Go、GOOS/GOARCH、CPU、
  GOMAXPROCS、命令、fixture SHA-256、HEAD/HEAD tree。每个 Body 核心 case 的 `B/op` 与
  `allocs/op` 至少下降 30%，`ns/op` 中位数不得回退超过 5%；超过时必须由 benchstat 证明
  差异不显著，或在验收报告中解释并重新确认；
- pre 与 post benchmark driver 必须分别作为独立证据冻结。pre driver 只用于证明开发前
  计时语义，不要求在 post API 上编译；机器 validator 必须校验 fixture、循环、attempt 数、
  `SetBytes`、计时边界、错误检查与 sink 消费语义等价，并把允许差异限制为声明的新旧 API
  适配。相对降幅必须从冻结的原始输出重新计算，不能信任元数据中的自报 `passed`；driver、
  原始输出、benchstat 输出和计算结果均须进入完整摘要链；
- `ReleaseCatalog.Resolve` 与版本画像 Resolve 必须达到 `0 B/op、0 allocs/op`；endpoint
  Resolve 可保留端点深拷贝分配，但不得再出现 map、JSON 编码或摘要计算分配；修改一次
  `Node()`、`Profile().Endpoints()` 或 `ExecutableProfile().Transports()` 返回值后，后续
  Resolve 必须完全不变；
- 稳定错误码使用可 unwrap 的 `RuntimeError{Code, Op, Err}` 与
  `RuntimeErrorCodeOf(error)`；包装后继续保持既有 `errors.Is`、`errors.As` 和 context
  错误链。Guard 只增加 `official_egress.guard.rejected`，细粒度原因继续使用现有
  `GuardReason`，不得建立第二套分类或从中文错误信息反向解析错误码；
- `BeginInvocation` 的初始化、Bundle／参数校验与 InvocationID 生成错误不得误标为执行策略
  拒绝；只有真实 `executionPolicies.acquire` 错误出口包装
  `official_egress.execution_policy.rejected`、`op=executor.acquire_policy`，并保留 minimum
  interval、并发等待 deadline 等原始错误链；
- Catalog 稳定分类为 `official_egress.catalog.load_failed` 与
  `official_egress.catalog.resolve_failed`。load 包装位于可注入 `fs.FS` 的真实加载入口，
  resolve 包装只位于失败出口；成功 Resolve 热路径不得增加接口调用、`defer`、动态类型判断
  或分配；
- 冲突 transition 必须由独立 validator 从冻结的变更集 5 baseline、post inventory 与 receipt
  复算单元 ID 增删集合、changed unit 数量、changed path closure 和全部摘要；错误 baseline、
  等量替换 ID、扩展变化路径、伪造计数或 receipt 均必须由 mutation 门禁拒绝。

任务顺序固定为：基线冻结 → pre benchmark → runtime Catalog 数据迁移与确定性导出 →
Catalog 启动期预编译 → attempt Body document 与不可变 backing → RuntimeError → 完整测试、
race、post benchmark、benchstat 和空允许列表 final-wire 验收。

## 四、与当前架构的差异

| 维度 | 当前架构 | 目标架构 |
|---|---|---|
| 身份判断 | 多数按平台、账号或 host 分散判断 | route 闭集显式解析 persona |
| Codex 版本 | 下游可能重新读取 active | 调用开始时解析一次不可变 Bundle |
| 包边界 | 画像与 fork 执行逻辑集中在 service | 纯画像、Executor core 和 transport port 下沉 officialegress |
| 请求构造 | 调用方可在 finalize 前后继续修改 | Plan 输入，Executor 定型后直接发送 |
| Header Override | 依赖各调用点顺序和保护函数 | Plan 中冻结，按 Header 所有权统一决策 |
| Executor 与发送栈 | 多个栈各自构造、部分已画像 | 唯一逻辑出口按 TransportSpec 编排多个 backend |
| OAuth refresh | 已画像但硬编码 active，并通过 req-profile 发送 | 消费同一 Bundle，保留已验证 req-profile backend |
| 用量刷新 | 普通 OAuth 默认合成 `hi` `/responses` | usage-only WHAM-first，严格校验并受控 fallback |
| 旁路发现 | 扫描已引用伪装符号的文件 | 类型感知扫描全部 terminal/facade sink，人工分类后由 CI 持续复算 |
| Guard 上线 | 缺少灰度与 Guard 回滚 | 未登记 route、无效 SinkBinding 分别控制；完整绑定的 sink 按 `legacy_observe → canary_enforce → enforced` 灰度 |
| 存量旁路 | 文件级或隐式容忍 | 精确 sink 基线只减不增，新增旁路立即失败 |
| 内部探针 | 主要关注请求形态 | 同时约束官方行为依据、频率、副作用和 fallback |
| Chrome 路径 | 与 Codex 同 host，缺少统一身份台账；wire 实测为 Chrome 120 + 导航 Header 混入 XHR | 保留独立 browser persona，TLS 与 HTTP 版本一致且形态为页面内 XHR |
| 上游合并 | 伪装判断散布在共享函数 | 高冲突文件只保留 Snapshot、Plan 和 Executor 薄钩子 |
