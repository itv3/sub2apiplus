# 出站画像 0.145 → 0.147 升级：为什么 20+ 轮没走通

> **技术路线评审 · 请外部工程师判断**
>
> 项目已推进 5 天、Campaign 编号排到 k57，尚未上线。本文列出可核验的现状数据、
> 卡点的机制性原因，以及三条备选路线，供外部评审判断技术路线是否需要调整。
>
> 日期：2026-08-12 ｜ 项目：Sub2API · OpenAI 官方出站 ｜ 当前 Active 仍为 0.145.0

---

## 01 要做的事

Sub2API 是一个 API 网关，它代理用户请求到 OpenAI 上游。为了让上游看到的流量与官方
Codex CLI 客户端无异，网关维护一份**「出站画像」**——一套逐字节的 wire 规格：
TLS 指纹、HTTP header 的精确顺序、body 字段的排列、连接复用行为等。

官方 Codex CLI 从 0.145.0 升到了 0.147.0，画像需要跟着升。要求是：升级后网关发出的请求，
在 wire 层面与真实的 0.147.0 客户端一致。

> **为什么标准定得这么严**
>
> 出站流量一旦与官方客户端有可识别的偏差，账号有被上游风控的风险。整套验收体系
> （逐规则采集真实官方流量、逐字节比对候选实现）就是为此建立的。这个出发点本身没有争议，
> 需要评审的是**实现这套验收的成本是否已经失控**。

## 02 两个数字的对比

分类阶段已完成对 0.145 与 0.147 官方源码及抓包的比对，结论是：

| 判定 | 条数 |
|---|---|
| `inherit`（行为未变） | **41** |
| `change`（新增一个 GET 路径） | **1** |
| 规则总数 | 42 |

也就是说，**两个版本之间真正的 wire 差异，是新增了一个 HTTP 接口**
（`GET /backend-api/wham/settings/user`）。其余行为逐条继承。

为验证这个差异所建立的机器：

| 项 | 规模 |
|---|---|
| 受管工具文件（.py / .sh / .json） | 97 |
| 验收 check | 150 |
| 候选采集任务 | 9 |
| 机器（生产 / 测试 / 备用） | 3 |

评审的第一个问题就在这里：**脚手架的复杂度是否与被验证对象的复杂度匹配**。

## 04 核心问题：20+ 轮作废，死因不在被验证对象

Campaign 编号从 k15 排到 k57。取记录最完整的 k42–k55 共 14 轮，逐轮死因分类如下：

| 死因性质 | 轮数 | 典型案例 |
|---|---|---|
| **验证工具自身的 bug** | 9 | 采集脚本把模型名写死成该账号没有的型号，第一跳 404；代理 host 写死，出站解析失败导致账号熔断、后续全部 503 |
| 操作失误 | 2 | 采集期间重建了容器 / 修改了账号配置，环境校验判定污染 |
| 环境或账号未备齐 | 2 | 账号套餐不支持所需模型；Campaign 冻结时缺参数 |
| 判据写错 | 1 | 规则期望值取自错误的证据面 |
| **0.147 行为搞不清** | **0** | — |

**14 轮里 13 轮的死因是验证机器和它的运行环境，没有一轮是因为搞不清 0.147 的行为。**

### 为什么一处出错要整轮重来

整个工具目录（97 个文件）计算**一个总摘要**。Campaign 建立时冻结该摘要，
此后任何一个文件改动一个字节，校验即拒绝继续：

```python
current_tool = _tool_identity(include_git=False)
if current_tool["files_sha256"] != manifest["tool_identity"]["files_sha256"]:
    raise ConfigurationError("升级工具摘要在 plan 后发生变化。")
```

该校验**不区分**：改的是产出证据的采集脚本还是只读证据的判据工具；改动是否涉及本轮已跑过的
任务；本轮是否已产出有效证据。

> **设计上的死锁**
>
> 工具在任务失败时提示「修复失败任务后使用 `resume --rerun-failed`」——
> 局部重跑的能力**本来就实现了**。
>
> 但只要「修复」动的是工具代码，上面那行校验就会拒绝 resume。而 14 轮死因里
> **9 轮正是工具代码 bug**，全部落在这个死角内。

循环长这样：

1. 建 Campaign，冻结工具摘要
2. 跑采集（官方 28 场景 + 候选 9 任务，耗时长）
3. 某个任务因工具 bug 失败——常常此轮该任务**零有效证据**
4. 修 bug（改一个字符串即可）
5. 工具摘要变化 → `resume` 被拒 → **整个 Campaign 作废**

↺ 回到第 1 步，官方 28 个场景一并重采 —— 已重复 20+ 次

值得注意的是，同一套代码对**环境**漂移做了正经的影响面分析：比对 service / containers /
account / configuration 四类探针快照，逐项列出漂移的种类，据此判断能否承接。
唯独对**工具**变化没有任何分析，直接一刀切。这更像是实现上的遗漏，而非有意的安全设计。

## 05 新发现的阻断：判据与画像互相矛盾

2026-08-12 定位到一处此前未被任何门禁发现的缺口，它使前述「分类与画像已完成」的结论不成立。

| 事实 | 取值 |
|---|---|
| 官方 0.147 抓包中该路径出现次数 | **107 次**（对比：`wham/usage` 5 次） |
| 官方 wire 形态 | `GET /backend-api/wham/settings/user` |
| 与其余同类接口的差别 | header 线序多一个 `cache-control` |
| 验收判据 A（路径集合） | **已包含**该路径 |
| 验收判据 B（header 线序） | 用 `not_equal` **显式排除**该路径（因线序不同） |
| 批准画像的接口清单 | 共 16 个接口，**不含该路径**；画像原文中该字符串不存在 |

两条判据都已针对这条新路径做了适配，说明**分类阶段确实识别出了它**；
但画像侧没有登记对应的接口定义。后果是网关在结构上无法生成该请求——
没有接口定义就没有 URL、header 闭集和线序可用，该判据永远不可能通过。

> **连带发现**
>
> 画像摘要 `0d86e033…` 曾被当作「画像内容未漂移」的证据，累计 16 次复算一致。
> 这条缺口说明**恒定也可能是「一直缺同一块」**——复算一致只证明每轮算出同一个值，
> 不证明该值覆盖了目标版本的全部出站面。
>
> 判据与画像出自同一次分类流程、写入同一批批准清单，两者的**跨清单一致性此前没有任何
> 门禁在校验**。建议评审此处是否应增加一道机器校验（用判据中出现的 path / header 集合
> 反查画像接口定义，取差集）。

好消息是官方证据本身完整（该路径就在这批证据里），**不需要回生产机重采官方流量**，
只需补画像接口定义并重新批准清单。

## 06 三条备选路线

### A. 修复局部重跑能力 【优先】

把工具身份从「一个总摘要」拆成按影响面分类，使「哪里坏修哪里、只重跑受影响任务」成立。

- **依据**：逐文件 sha256 清单**已经在记录**，只是校验时只比总摘要；`resume --rerun-failed`
  也已实现。缺的是影响面判定。
- **粒度**：产出侧（采集脚本、探针、中继、脱敏——决定证据内容）严格冻结；评估侧（契约、
  门禁、断言——只读证据做判断）允许改动后重新评估。历史上多轮作废的修复正属评估侧。
- **收益**：直接消除第 04 节描述的死锁循环。
- **风险**：放松了证据链约束。需以白名单 + fail-close 设计（未分类文件默认按产出侧处理），
  并要求收据记录变化文件清单以备审计。
- **时机**：当前无活跃 Campaign，是改造的安全窗口。

### B. 收缩验收范围

既然 41 条规则判定为 `inherit`，不再对其做全量采集验证，改为验证真正变化的 1 条 +
对 inherit 结论做抽样确认。

- **收益**：9 个采集任务可压缩到 2–3 个，判据从 150 项降到数十项；工具面缩小后自身出错
  概率同步下降。
- **风险**：`inherit` 结论来自源码 diff 分析，抽样验证不覆盖的部分将失去实测保障。
- **待评审**：抽样比例与选取策略；哪些规则即使 inherit 也必须全量验（如 TLS 指纹、
  连接生命周期）。

### C. 跳过离线验收，直接灰度

建立 0.147 画像后直接 canary，用真实流量的错误率与风控信号替代离线逐字节比对。

- **收益**：最快。
- **风险**：画像若有偏差，代价是账号风控——这正是整套验收体系存在的理由。除非有独立的、
  低成本的偏差检测手段，否则不建议。

## 07 希望外部评审回答的问题

1. **验收体系的复杂度是否已经失控？**
   用 97 个受管文件、150 项判据去验证「新增一个 GET 接口」，是否符合比例？
   如果重新设计，合理的验收规模应该是什么量级？

2. **工具身份一刀切冻结，是有意的安全设计还是实现遗漏？**
   既然同一套代码对环境漂移做了细粒度影响面分析，对工具变化不做，是否有我们没看到的
   安全考量？方案 A 的产出侧/评估侧划分是否成立？

3. **41 条 `inherit` 是否值得全量实测？**
   源码 diff 判定为「行为未变」的规则，在什么条件下可以免于逐条抓包验证？

4. **判据与画像的跨清单一致性**，除了本文建议的差集校验，还有哪些同类矛盾值得预先设防？
